# Alcydeo 0.2.0 — privacy notice

Updated November 14, 2026 for the first public GitHub preview. Documentation: https://drslid.github.io/Alcydeo/ ; public support: https://github.com/drslid/Alcydeo/issues ; private security reporting: https://github.com/drslid/Alcydeo/security/advisories/new . No Chrome Web Store or Firefox/AMO listing is claimed.

Alcydeo automatically detects media on HTTP/HTTPS sites by default, including embedded player frames allowed by Chrome. These host permissions are declared at installation. The user can pause detection in Alcydeo or limit site access in Chrome; restricted hosts are not observed. It handles page titles, page/media URLs, available qualities, duration, file sizes and technical track metadata. It does not collect account profiles, payment data, typed forms, spoken content or advertising identifiers. It does not read cookie values through an extension API.

Page detection results, observed redirect aliases and rejected HTML source URLs are stored in Chrome session storage and cleared on navigation/tab closure. Pending redirect chains stay in a bounded in-memory cache (256 requests, at most 20 URLs each, pruned after 60 seconds on new events). Rejected source URLs are capped at 200 per tab. Download tasks, library records, source/page URLs, optional favorites, timestamps, checkpoints and technical validation results are stored in the extension's IndexedDB. Source URLs may include authentication signatures needed for recovery. These are local profile data, not an encrypted secret vault. Do not share a browser profile containing sensitive task data.

Segmented media fragments and generated files are staged in OPFS, subject to Chrome's quota and eviction behavior. Remove a task to remove its record and temporary directory. A final file saved through Chrome stays in the user's download folder; deleting the library record does not delete it or erase Chrome's download history. Removing the extension removes its extension storage, but not saved download files or browser-managed history.

The extension has no Alcydeo server, account system, advertising or telemetry. The installed extension checks the documentation URL only when Help is clicked, and opens the site if published. Offline or before publication it shows local help. No library data or media is sent to the documentation site. Native downloads and allowed media requests contact the original source/CDN and use Chrome's applicable network/session handling. Source providers may therefore receive the user's IP address, ordinary request information and session credentials managed by Chrome. Site host permissions do not guarantee that every authenticated source or CORS configuration will work. No DRM or access protection is bypassed.

The background can fetch HLS/DASH playlists already observed in authorized page traffic to identify qualities and exact initialization/media fragment URLs, even while the popup is closed. It attempts at most 24 unique observed playlist URLs per tab navigation. The popup can also fetch detected HLS/DASH playlists to present and group their qualities. These are metadata requests to Chrome-authorized source/CDN hosts, not media-segment downloads. Fragment associations are retained in session storage, capped per tab at 4,096 exact URLs and 262,144 URL characters (about 512 KiB of UTF-16 text), with currently observed candidates prioritized. These associations and inspection markers are cleared on navigation/tab closure. Navigation, pausing or changing access aborts affected active metadata requests; stale results are discarded. Popup lookups are limited to sixteen source URLs per popup; background and popup share two active requests, an eight-second timeout per active lookup and a two-megabyte response limit. The background queue is capped at 32 waiting lookups and parsed manifests at 200 variants. Each HLS lookup can follow up to six playlist levels only when there is a unique rendition; a branch is offered as a quality choice without loading every rendition or any media segment. The two-megabyte cap applies per playlist response. Download planning can follow the selected quality through up to six levels per track, with the same host checks and a shared twenty-second timeout for the video/audio plan. A failed lookup leaves the manual quality action available. Source-family comparison keys are used only for grouping; the original signed URLs are retained for downloads.

Metadata exports are initiated by the user and omit source/page URLs, signatures, disk paths, download IDs, checkpoints and cookies. They contain titles, optional tags/favorites, dates and technical validation metadata. Error messages use bounded local codes rather than raw response bodies or signed URLs. No automated diagnostic upload exists.

Incognito use is disabled in the manifest. Site access can be restricted in Chrome's extension settings. Pausing automatic detection removes its registered observers and native request listeners, including those on individually allowed sites. The extension stores finite site grants locally to preserve Chrome's choices across restarts. A native transfer returning an HTML error/session page is stopped; any already completed bad file from that transfer is removed instead of being presented as a saved video. The Chrome Web Store and browser may separately handle distribution and browser diagnostics according to their own settings and notices.

Native handlers are registered synchronously against the manifest's required HTTP/HTTPS declarations so Chrome can wake its service worker. Chrome enforces site restrictions; handlers also await restored preferences and check access before retaining any media. Filters are then narrowed to actual grants or removed when detection/access is disabled. Version 0.1.3 applies the user's requested automatic-detection default once on upgrade and stores a local migration marker alongside settings. Other preferences are preserved; later explicit pauses remain in effect across restarts.

The prepared static documentation would be hosted by GitHub Pages only after explicit publication. Visiting that site contacts GitHub and may create hosting logs; the site does not add analytics or a media proxy. A native optional TV prototype exists, with receiver playback unvalidated and AirPlay unavailable on the current Chrome target. Optional cloud uploads are described below.

Before a Store submission, the publisher must provide a real support contact, publish the matching privacy page and complete the Store's data-use disclosures. Local-only handling must still be disclosed: [Chrome policy guidance](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq).

Saved segmented-task records can include a local notice that timed metadata (MPEG-TS type 0x15) was omitted during remux. This code contains no metadata payload or navigation URL and is translated locally. Unknown stream types retain diagnostics and are refused rather than silently exporting incomplete audio/video.

Detection observers start at document_start on Chrome-authorized HTTP/HTTPS pages. Relevant media/iframe/link changes are coalesced; unrelated DOM updates do not request a scan. Automatic scans skip thumbnail generation; opening the popup can request that detail. Frame execution and restoring observers in other tabs do not block publication of an already observed media response. This changes scheduling, not permissions, retained data categories or telemetry.

Saving preferences consist of a relative download subfolder and a Save As boolean in Chrome local settings. New tasks retain that choice in IndexedDB; older tasks use the current settings. No directory handle, absolute destination access, filesystem permission or new host permission is acquired. The directory shortcut opens chrome://settings/downloads only when clicked. Automatic writes and per-file Save As both use Chrome’s downloads API.

The experimental local build can read the already-loaded YouTube player catalog and observe ordinary player POST requests to googlevideo.com. A request body is bounded at 128 KiB and decoded only to retain its stream id/endpoint, opaque Ustreamer context, client name/version and existing opaque transport token when present. Other client/device fields are discarded. The opaque context/token can carry session identifiers and is not telemetry. Up to sixteen contexts per tab live in extension session storage and are cleared on navigation/tab closure. A queued task retains its selected context locally in IndexedDB until the task is removed; exports omit this data. No cookie values are read, token is generated, attestation challenge is run, or remote player JavaScript is fetched/executed. A server attestation refusal stops the transfer without saving partial media. The Store build removes the YouTube catalog/transport code at compilation and retains its host exclusion.

Page scanning now covers bounded open shadow roots and recognizable already-loaded media resource URLs. Closed component internals are not inspected; their ordinary network/media timing records can sometimes identify a source. Native pages, inaccessible frames, encrypted/live streams and unsupported player protocols remain outside guaranteed coverage.

Since version 0.1.12, Alcydeo also observes embedded-document response headers, so an HTML player wrapper is not offered as a media file. Content-Disposition filenames are parsed transiently (4 KiB header bound) to reject HTML attachments even under a generic binary MIME type; no new filename field is retained. Known script/image/iframe/style resource timing entries are not treated as downloaded media. HTML error responses, including 403, are rejected without a body fetch. Generic binary sources require a media suffix on the actual URL path. Proxy file/cdn parameters are not used to invent a destination; only normal observed redirects can associate the final signed URL with its player. No new permission, request-header rewriting, background metadata probe or token generation is added.

The optional multi-part setting stores a boolean and a 2/4/8 request count in local preferences. New direct-file and DASH tasks retain the selected mode/count and their existing save destination. The range checkpoint details below apply to direct files; monofile DASH retains only complete-resource checkpoints, as detailed in the 0.1.46 note. The Worker probes a one-byte range and uses Range/If-Range with the source's strong ETag; it does not rewrite authentication headers or create signatures. A resumable checkpoint stores the ETag, total size and each part's start/end/received byte count in IndexedDB. One OPFS output file retains downloaded bytes until task deletion. Checkpoints commit after an OPFS flush, at least at part completion and approximately each 4 MiB or second of progress. Those fields are excluded from metadata exports.

Disabling the option affects new tasks. The manager must stay open during multi-part processing; closing it stops its Worker, and the existing lease/recovery path exposes a paused task. Compatible retries reuse flushed bytes against the same source version; changed validators/size, malformed ranges, HTML and insufficient space stop the task without saving a partial file. Fresh incompatible sources revert to Chrome's ordinary direct transfer and retain the chosen Save As/subfolder settings. No new extension permission or network service is introduced.

The 0.1.14 revision replaces local brand images and icons. It adds no data collection, network request, permission or transfer behavior.

The confirmed Clear history action captures the eligible local record IDs when opened and rechecks their states in an IndexedDB write transaction before deletion. It covers all list pages and search/favorite filters, including favorite records. It removes eligible finished/failed/cancelled records and their OPFS directories, including native files already saved. It keeps saved downloads, Chrome’s own download history, queued/active/paused work, live worker leases and newly created records. Pagination renders 20 matching entries per page; it adds no new data category, permission or network service.

Local MP4 conversion requires an explicitly selected File, or a manager output already held in OPFS. The task retains the selected filename as its title, byte count, optional source-task ID, input-ready flag and codec-copy/reencode flags. No source absolute path, external directory handle or implicit access to Chrome’s downloaded files is obtained. The source copy and generated MP4 remain in the task’s OPFS directory until record/history deletion; the original disk file and saved output are kept. Conversion itself sends no HTTP request. The packaged AAC fallback executes local WASM in a local Worker when needed; CSP permits wasm-unsafe-eval but not JavaScript unsafe-eval, remote execution or Blob workers. Queued inputs persist locally; interrupted codec processing restarts from that input.

## Explicit capture, editing and cloud operations (0.1.17)

Recording starts only on an explicit action: the current authorized tab from the real Chrome toolbar popup via tabCapture, or a surface chosen through Chrome’s getDisplayMedia dialog in the manager. Chrome displays its capture indicator. Neither path requests camera or microphone. A persistent extension page owns the stream and must remain open. The default is up to 1080p/30 fps, with 720p or source up to 4K selectable. MediaRecorder uses locally available VP9 or VP8 with Opus, 8–32 Mb/s video and 192 kb/s audio; actual detail depends on the source and computer. One-second chunks are flushed to OPFS through a Worker, with at most 16 MiB pending. Slow storage stops with a notice. Flushed bytes can be recovered after interruption; capture cannot resume without a fresh explicit action. The selected surface includes all visible page content. The tab-capture audio is also routed locally so recording does not silence the user’s player. Annotation strokes remain in the source tab’s isolated local overlay, use no network and are removed when capture ends.

Compression, trimming and merging remain local. Selected inputs are copied to OPFS and processed sequentially with the existing codec Worker. Merge intermediates are removed after success/failure; prepared inputs and completed output remain until task/history removal. Originals on disk remain unchanged. Download support for a container does not imply decoding/conversion support for every codec.

Cloud uploads are initiated by the user for a selected file or a retained local result. Alcydeo has no own relay/backend. Gofile receives a multipart upload without an account sign-in and creates a **public link**: anyone with that link can access the file. Provider retention rules apply. Google Drive and OneDrive were removed at the user’s request in 0.1.30. No account connection is offered. The user’s chosen provider receives the file contents, filename, size, MIME type, IP address and ordinary connection information. No source-page URL or browsing history is sent as upload metadata.

pCloud deposits use an existing upload-link code and the folder’s chosen data region. The sender does not authenticate in Alcydeo, but the folder owner needs a pCloud account. The selected file is uploaded directly to api.pcloud.com (US) or eapi.pcloud.com (EU). Alcydeo does not read or copy cookies or add OAuth tokens. Chrome may nevertheless attach provider cookies to the existing Gofile/pCloud XHR transport; the explicit credential omission tested with pre-existing cookies applies to MegaUp. No new public download link or email is created. The reusable upload link and region remain in local extension preferences; each unfinished job retains its own destination code. That per-job code is cleared on completion or cancellation. A retained upload link grants deposit access: removing a job does not revoke the link or delete the remote file.

The manifest contains no identity permission or OAuth configuration. Upgrade clears former session-token entries and the former OneDrive client-ID preference. Legacy Drive/OneDrive jobs remain identifiable for cancellation/removal, but cannot resume. This local cleanup does not revoke a previously granted provider consent or delete a provider’s file; provider settings govern that.

Cloud jobs use a separate local IndexedDB and a dedicated OPFS copy so staged input cannot change. Uploads use no source-site cookies. Gofile and pCloud restart the entire upload after interruption, only after explicit retry. A manager closure leaves interrupted uploads for explicit resume after ownership expiry. Files staged for completed uploads are removed. Removing a Cloud entry clears its local job/copy and never deletes a remote file. Cancel aborts local requests; a provider may have received bytes before cancellation or a lost response.

[Gofile](https://gofile.io/privacy) and [pCloud](https://www.pcloud.com/privacy_policy.html) apply their own terms. The current pCloud fix includes a read-only check of a supplied upload link; no file was sent. Upload protocol tests use intercepted local responses and are reported separately from user-reported provider success.


The 0.1.18 workspace redesign changes presentation, navigation and locally formatted counts/dates derived from existing task records. Icons are locally bundled Google Material Symbols SVG path data under Apache-2.0. No icon/font request, permission or new retained data category is introduced. Add a video reuses the existing explicit local-file processing dialog; sidebar Help uses the existing documentation availability check.
