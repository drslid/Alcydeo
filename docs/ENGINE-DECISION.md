# Local media engine — prototype decision

Research and implementation date: 2026-11-01. Windows Chrome 156.0.8078.76 is the user's target. Linux Chrome for Testing is the available automated environment; these are separate validation targets.

The performance target is to avoid unnecessary work: Chrome downloads for direct sources, packet copying without decoding for compatible segmented sources, bounded network concurrency, disk-backed fragments and incremental MP4 output. No claim of being the fastest downloader is made.

| Candidate | Evidence and scope | Decision |
| --- | --- | --- |
| Native `chrome.downloads` | Browser-managed direct downloads, pause/resume when the source permits; no extension-sized media buffer | Direct-file path. User selects the saved file for a real local content check. |
| Mediabunny 1.65.0 | TypeScript, lazy Blob reads, TS/fMP4 demux, encoded-packet sources, streamed output, WebCodecs integration | First remux engine; bundled locally in a Worker. MPL-2.0 retained. No codec encoder is added for this slice. |
| MP4Box.js 2.5.0 | Incremental MP4 parser, segmentation, sample extraction; BSD-3-Clause | Measured as a metadata-parser alternative. It does not by itself provide the full HLS/TS/DASH download pipeline. |
| mux.js 6.3.0 | TS-to-fMP4 transmuxing; Apache-2.0 | Measured as a specialized TS alternative. Broader container handling and task recovery would still be required. |
| ffmpeg.wasm | General codec/container coverage, but additional runtime size, memory and CPU costs | Not included in this slice. Reconsider only for a measured conversion need. |

Primary sources:

- [Chrome downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)
- [Mediabunny source](https://github.com/Vanilagy/mediabunny), [streamed output and backpressure](https://mediabunny.dev/guide/writing-media-files)
- [MP4Box.js source and incremental parsing](https://github.com/gpac/mp4box.js)
- [mux.js source and transmuxing example](https://github.com/videojs/mux.js)
- [ffmpeg.wasm published benchmark](https://ffmpegwasm.netlify.app/docs/performance/): an old Chrome 116 transcode measurement, not a benchmark of Alcydeo or a current comparison with Mediabunny.

Run `pnpm bench` for the local microbenchmark. Results go to `artifacts/benchmarks/engine.json`. The cases deliberately identify different operations; their numbers must not be presented as a fair universal engine ranking. Browser task timings, output validity and temporary-storage behavior must be assessed separately.

Resource policy: one segmented task at a time, three concurrent fragment fetches, up to eight tracks, 4 MiB input cache per input, 1 MiB output chunks. These are implementation settings, not measured peak-memory claims. Fragments, concatenated inputs and output currently coexist in OPFS: plan for approximately three times the media size plus filesystem overhead. Interrupted fragments are refetched. Confirmed fragments are reused only with a matching strong ETag; otherwise they are refetched. Signed URL refresh and different media versions must never be silently combined.

## Segmented compatibility in 0.1.6

MPEG-TS `stream_type 0x15` carries timed metadata (commonly ID3); it is not a video codec. The pinned demuxer already omits that track. Alcydeo uses Mediabunny’s public logging API to collect that specific condition as a persisted, localized information note, while audio/video remux and file validation still run. Other warnings remain visible. Other unsupported MPEG-TS stream types stop the export with a codec diagnostic, avoiding a nominally completed video that contains only audio. No demuxer source patch or remote code is used. [Apple’s timed-metadata format](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/HTTP_Live_Streaming_Metadata_Spec/2/2.html), [pinned library logging source](https://github.com/Vanilagy/mediabunny/blob/main/src/logging.ts).

Observed playlists are inspected with two active metadata jobs, up to 24 unique observed URLs per tab navigation, an eight-second timeout and a two-megabyte response limit. Popup requests share the queue. Only explicit playlist relationships classify opaque MP4 URLs as fragments; no sequence of numbered files is invented. The exact-URL session cache is capped at 4,096 entries / 262,144 URL characters per tab. Currently observed candidates are prioritized. Very large or inaccessible manifests can still leave unidentified candidates, and DASH associations currently follow the default selected representation and audio plan.

The new synthetic browser corpus includes H.264/AAC TS plus real timed-ID3 PES packets, CMAF init/media fragments with opaque .mp4 names, and HLS `EXT-X-MAP` with explicit byte ranges into a single MP4. The Worker checks the exact HTTP Content-Range, rejects HTML fragments before writing them and verifies the resulting MP4. Implicit initialization-map offsets, discontinuities, live windows, encrypted sources and multi-period DASH remain outside the implemented subset.

Regenerate this additional corpus with `FFMPEG_FOR_FIXTURES=/path/to/development/ffmpeg node scripts/segmented-fixtures.mjs`. FFmpeg is used only to prepare/check original synthetic fixtures; no FFmpeg runtime or native companion is shipped.

## Badge latency in 0.1.7

The 0.1.6 detector registered observation at document_idle, used default-time DOM injection while holding the media-cache lock, and awaited restoration of observers in all open tabs before processing media headers. Controlled loading fixtures reproduced delays of 2.3–3.0 seconds after the source was already available.

Observation now starts at document_start. Automatic scans inject immediately, omit thumbnail generation, and collect frame results outside the per-tab cache lock. Their commit reads the latest cache and checks the navigation generation. Concurrent scans are coalesced. The first relevant event schedules a scan immediately; subsequent automatic scans are limited to one start per 200 ms. A 40 ms content notification batches relevant mutations. Unrelated DOM updates are filtered, observer reinjection cleans up the previous instance, and detailed popup scans can request previews.

Permission/settings restoration still gates native responses, while reinjection into existing tabs runs separately with three active restoration workers. The cache is persisted before updating the badge. Quality analysis remains asynchronous. Only top-level navigation clears its context; a loading notification from another frame no longer clears an existing badge.

Five actual-extension cases cover parser-blocking resource loading, a loading frame plus delayed quality lookup, unrelated DOM churn, worker wake with another loading tab, and a frame executing blocking JavaScript. The badge tests use Chrome action API state, not a simulated UI or a painted native-toolbar measurement. For the busy-renderer case, the reference timestamp comes from the local fixture server, and the result is checked against the real JavaScript blocking interval. These are local controlled cases on Linux Chrome, not a universal timing guarantee on Windows or real providers.

[Measured 0.1.6 baseline](benchmarks/badge-before-0.1.6.json), [0.1.7 measurements](benchmarks/badge-0.1.7.json), [Chrome injection timing](https://developer.chrome.com/docs/extensions/reference/api/scripting#type-ScriptInjection), [Chrome runAt definitions](https://developer.chrome.com/docs/extensions/reference/api/extensionTypes#type-RunAt).

## HLS list resolution in 0.1.8

The previous planner parsed the selected HLS URL once and raised `chooseQuality` whenever the response was still a master. This was mapped to a generic unsupported-stream message. A local case reproduces a displayed 1100p wrapper above the actual 404p/180p choices; the old production build never exposes that inner branch. This is a controlled reproduction of the reported failure path, not a recording of Zalando’s manifest. The real supplied product page was inaccessible from this environment: [access evidence](benchmarks/zalando-source-0.1.8.json).

Discovery now follows a unique rendition until it reaches a branch or media segments. It does not expand every branch or download media fragments. A child on a Chrome-restricted CDN is returned as a visible permission target without requesting it. Download planning follows the selected rendition, preserving exact signed URLs, its resolution and inherited separate audio. A unique child is unambiguous; a branch matches the selected resolution/rate, or stops with a dedicated recovery message. A choice without any quality metadata defaults to the highest advertised rendition.

A chain is limited to six playlist reads, with at most 200 variants and two megabytes per response. Discovery retains two active jobs and an eight-second timeout. Video/audio plan resolution shares a twenty-second timeout, with up to six reads per track. Exact URL cycles stop before a duplicate read. Changed signed URLs remain exact and still count toward the depth bound. Every request checks Chrome’s host permission; protected manifests are rejected before a key/media request. Nested HTML is classified as HTML. Parsed playlist relationships are kept separate from HTTP redirect aliases.

[HLS RFC 8216](https://www.rfc-editor.org/rfc/rfc8216#section-4.3.4.2) defines a master variant URI as a media-playlist URI. Nested master wrappers are tolerated here as a bounded compatibility extension; they are not described as a requirement of that standard. Neither a successful fixture nor an inaccessible site establishes universal provider compatibility.

## Compact proposals and saving in 0.1.9

Source proposals use a single-line full-tooltip title, compact quality/download controls and only a real video-frame thumbnail. The filename editor and decorative thumbnail placeholder have been removed at the user’s request. Explicit preview remains available and uses the currently selected direct variant. A six-source long-title fixture measures 100 px per card with three fully visible cards at 525×600; no horizontal overflow.

Both direct transfers and assembled OPFS outputs share destination options: automatic saving (`saveAs: false`) or native per-file Save As (`saveAs: true`). New tasks persist their queue-time folder/mode; legacy tasks fall back to current settings. Automatic mode keeps the native download engine and its large-file path. The extension supplies a relative subfolder inside Chrome’s chosen main download directory. A click-only shortcut opens Chrome’s directory settings; it does not change global browser preferences itself. Arbitrary extension-specific absolute destination handles are not implemented. Chrome’s downloads API documents [relative filename and saveAs options](https://developer.chrome.com/docs/extensions/reference/api/downloads#type-DownloadOptions).

The real Chrome automatic-mode tests use an isolated profile with a selected default directory and restore native download behavior, verifying actual direct/HLS files in Courses/2026. Save As tests observe the unchanged true flag at both extension API boundaries and complete transfers with an explicit headless CDP directory override. That override can ignore the proposed relative filename and is not evidence of a Windows chooser being painted or accepted. Chooser dismissal is simulated only at the rejected API call: direct Retry then performs a real native transfer; assembled Retry saves the existing validated output without reprocessing. A declined assembled save stays available and never opens repeated automatic choosers.

## Experimental local YouTube transport (0.1.11)

The current desktop player tested exposed SABR/UMP rather than direct format URLs. Its ordinary POST already contains the transport initialization context. The implementation reads only that existing request and already-loaded format catalog; no remote executable, signature decipherer, token minting, native companion or backend is introduced. Already-exposed direct audio/video URLs also use the existing two-track remux pipeline. One grouped card keeps the actual format itags as quality ids.

[googlevideo 5.0.1](https://github.com/LuanRT/googlevideo) provides the bundled MIT SABR reader and protobuf models; [SabrStream API](https://ytjs.dev/googlevideo/api/exports/sabr-stream/). Its video/audio queues are bounded at 1 MiB/256 KiB and chunks are written progressively to OPFS. A single selected task is processed at a time; stream-body retries are capped at two (the shared HTTP helper separately permits up to four attempts for transient status responses). Source HTML is rejected and server attestation refusal aborts immediately. No callback generates or repairs proof-of-origin tokens. Storage is checked initially and every 16 MiB; selected format metadata is capped at 200 entries. An interrupted SABR transfer restarts from the beginning: segment/snapshot recovery is not implemented for this experimental transport. HLS/DASH checkpoint behavior is unchanged.

Complete separate-track and UMP assembly is validated on original six-second synthetic media. That fixture does not establish real YouTube compatibility. The user watch URL exposed eight qualities and badge 1, but a real 240p transfer was refused after initial fragments; no complete file of that video was exported. After rejecting optional cookies through the ordinary consent screen, the supplied Short completed with AVC/AAC, 48.623 seconds: 1,300,696 bytes at 144p and 6,624,539 bytes at 720p (720×1280 portrait). The actual saved file fully decoded. Audio format xtags are retained to identify the source track correctly; equivalent portrait renditions share a quality choice. High resolutions and YouTube codec combinations remain unvalidated.

The default local artifact and explicitly separate `pnpm zip:store` artifact have different compiled capabilities. The latter excludes YouTube transport code and retains host rejection. This does not imply Store acceptance: [Chrome prohibited functionality](https://developer.chrome.com/docs/webstore/program-policies/malicious-and-prohibited) and [developer terms](https://developer.chrome.com/docs/webstore/program-policies/terms) still require publisher review and authorized uses. No package is submitted.

## Generic binary CDN files and HTML wrappers (0.1.12)

Two actual-extension fixtures reproduce the old failure: a blob player fetching through a PHP proxy has no badge, while a direct video element keeps the proxy/reader URL. The final response is an ordinary MP4 served as application/octet-stream. Accept generic binary MIME (or absent MIME) only with a recognized media suffix on the actual path; do not infer a file from a query parameter. Preserve HTML priority and known segment exclusions.

The existing redirect association then retains the exact final ff query and correct native download destination. Content-Disposition HTML filenames, HTML error responses including 403, and embedded HTML documents are rejected; known script/image/iframe/style resource timing entries are excluded from recovery. Redirect response bodies are ignored because their HTML does not describe the final payload. No probe, new permission, challenge handling or header rewriting is introduced.

Before/after browser tests cover an XHR-to-blob player and a normal video element, two cross-host redirects, one proposal/badge, preserved signed query, native output byte equality, local track/duration/playback validation and service-worker replacement. The supplied Webflix page loaded but its normal player was blocked by a security verification in Chrome for Testing; no full film was downloaded and the exact provider remains unverified. The reported user URL is an example, not evidence of that CDN's current response type in the user's session. [Chrome's event/redirect semantics](https://developer.chrome.com/docs/extensions/reference/api/webRequest) support matching request ids across normal HTTP redirects.

## Optional direct-file multi-part transfer (0.1.13)

The user requested a selectable accelerator. Preserve native Chrome downloads by default, and offer 2/4/8 simultaneous range requests with a default count of 4. These are logical HTTP requests; Chrome controls TCP/TLS connections and HTTP/2 multiplexing, so a selected count is not a promise of that many physical sockets. Existing HLS/DASH concurrency and SABR transport are unchanged.

A Worker probes GET Range bytes=0-0. It requires an actual 206, an exact Content-Range with a safe known total, identity content encoding and a quoted strong ETag. Direct files smaller than 1 MiB use the native path to avoid overhead. A fresh source that ignores ranges, omits a strong validator or cannot be safely probed uses Chrome's normal direct transfer; a known partial transfer never silently changes version. Explicit HTML, HTTP access failures and revoked permission remain errors. Redirected extension fetches are not followed; a fresh probe's fetch incompatibility can fall back to the existing native path.

[HTTP semantics, If-Range and partial-response combination](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) require strong validation when combining responses. Each part carries If-Range; every 206, ETag, Content-Range, byte count and encoding is checked. Changed or malformed responses abort all active requests. The exact selected URL/signature is used throughout.

[OPFS synchronous access handles](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle) allow one Dedicated Worker to write each chunk at its file offset. This avoids whole-file buffering, separate part files, a concatenation copy and remux for direct media. One exclusive handle belongs to the task's existing lease owner. Flushed progress is persisted after about 4 MiB or one second, and at part completion/stop. On resume, the same validator/size and the OPFS file size must agree before received byte counts are reused. Network inactivity is bounded at 120 seconds and shared HTTP retries remain bounded. Pause/cancel state is checked independently of manager visibility; ownership renews every eight seconds.

The completed original file receives structure, tracks, duration and initial playback checks before Chrome saves it. Its extension and bytes are preserved. Saving still uses the queued automatic/Save As and subfolder choice, and retries of a prepared output use that output. Native MIME rejection applies to external direct transfers; validated manager-produced output is handled as such. Temporary OPFS space is about one source file, in addition to the final saved file. Chrome quota and storage overhead still apply.

The original 1.8 MB throttled fixture measured approximately 4.53 s for one response versus 1.17 s for four ranges, with each response limited to 16 KiB/40 ms. This is a controlled throughput experiment, not an Internet or Chrome-native speed guarantee. The 2,203,363,043-byte repeated course was copied with four ranges and matched its original SHA-256. Neither test establishes arbitrary codecs, sources or file sizes. Exact final evidence is in TEST-RESULTS.md.

## Local MP4 conversion (0.1.16)

Settings has one video picker and no codec, quality or concurrency menus. Applicable records offer Convert to MP4; native saved originals require explicit file selection because Chrome’s downloads API does not grant file-content access. Existing manager outputs can be read locally. No source file is renamed or overwritten.

The target is H.264 AVC with AAC-LC audio when the source has audio. Compatible AVC profiles and AAC-LC packets are copied. Other supported tracks use Mediabunny Conversion and Chrome WebCodecs; reencoding can change quality and take time. Reencoded audio uses 48 kHz, preserves its channel count and selects 192–512 kbit/s according to channels. Display dimensions are rounded up to even values only for reencoding; contain fitting preserves the aspect ratio. All audio/video tracks must survive preflight and final validation; unsupported tracks fail without a saved partial/audio-only MP4. Subtitles, HDR/tone mapping, unusual multi-track combinations, other output containers and large/long reencoding remain unvalidated.

A local File streams into OPFS without a whole-file ArrayBuffer. Prepared inputs and task metadata persist. An atomic IndexedDB lease serializes conversion jobs across managers; an exclusive Worker Web Lock reinforces this. A paused/interrupted conversion restarts from the saved input, rather than claiming codec-state checkpoint recovery. Ownership renews every eight seconds; manager-closure recovery uses the existing thirty-second lease. Cancellation aborts the codec pipeline and exports no file. Temporary inputs/outputs remain local until task/history removal; saved originals and MP4 files are kept.

The actual Linux Chrome 156 capability probe supported AVC but not AAC encoding. A pinned @mediabunny/aac-encoder 1.65.0 fallback supplies AAC only when the requested native audio configuration is unavailable. Its worker body and embedded WASM are unchanged; scripts/conversion-assets.mjs replaces the upstream Blob-worker factory with a packaged Worker. JavaScript eval, Blob workers and remote executable fetching remain unnecessary. CSP adds only wasm-unsafe-eval. The fallback is not a general FFmpeg runtime or native installation.

The AAC wrapper is MPL-2.0 and the embedded FFmpeg AAC encoder is LGPL-2.1-or-later. Exact package sources, the MV3 adaptation, rebuild instructions and LGPL text are included in the package’s licenses directory. A matching FFmpeg source archive for commit 60a2818f76dcd1fee3155b1791304af104a0fc1b is prepared in ignored artifacts, with its hash in benchmarks/aac-source-0.1.16.json, for corresponding-source distribution alongside any later authorized release. Nothing is published during preparation.

Primary documentation: [Mediabunny conversion](https://mediabunny.dev/guide/converting-media-files), [formats/codecs](https://mediabunny.dev/guide/supported-formats-and-codecs), [AAC fallback](https://mediabunny.dev/guide/extensions/aac-encoder). Installed 1.65.0 source and real Chrome outputs, rather than a current website claim alone, determine the implemented subset. Current evidence is recorded in TEST-RESULTS.md.


## HLS live stream recording — 0.1.24

The Record workspace now separates Player stream from the existing Tab capture workflow. The new mode accepts an authorized detected HLS source/quality or an explicit .m3u8 URL. It records complete unencrypted muxed TS/fMP4 segments from a recent segment near the live edge, writes chunks to a Worker-owned OPFS sync handle and checkpoints only complete flushed segments. Counters and the last sequence/URI/range are persisted; the task does not accumulate an in-memory list of the broadcast. Polling uses target duration after changes and half target duration for unchanged playlists, following [RFC 8216 §6.3.4](https://www.rfc-editor.org/rfc/rfc8216.html#section-6.3.4).

An explicit Stop waits for the current bounded segment request to finish. ENDLIST also finishes the recording. The source is remuxed to MP4 using encoded packets, checked for tracks/duration/initial playback and saved through Chrome. No screen chooser, video encoder, remote engine or native companion is involved in this path. The separate visible-tab recorder remains WebM VP8/Opus at up to 480p/24 fps.

Missed sequences, a changed last-segment identity, a continuity/map change, expired or HTML responses stop collection. The contiguous committed part may be finalized, with a partial-recording notice and a persisted reason. Cancellation exports no file. Closing every processing manager terminates the Worker; after lease recovery, Save captured part truncates any unfinished tail to the committed byte boundary and remuxes locally without requesting the source again. It does not restore missed broadcast time. A persisted stop is observed by the Worker even if the runtime notification is lost.

Scope: combined audio/video HLS TS and fMP4 only. Separate-audio renditions are refused before a task starts, rather than exporting video without its sound. DASH dynamic, encryption, I-frame-only and delta playlists are refused. LL-HLS is usable only when normal complete segments are also available; partial fragments are not assembled. Discontinuity stitching and arbitrary program/codec changes are not supported. A pasted multi-variant master currently follows the resolver's default rendition; use a detected quality or an explicit child URL to select another.

Storage grows with the received stream. Collection reserves space for final remux with a safety margin; OPFS remains quota-bound and not absolutely durable. There are at most 100,000 committed segments per session, a bounded manifest size and segment timeouts; these are technical bounds, not paid quotas. Finalization rewrites the recording on disk and may take time for large captures. Only short original synthetic broadcasts are measured in this release. fMP4 sample hashes are preserved in the fixture; TS framing changes during remux, so file/sample byte identity is not asserted for TS. Both tested outputs retain 144 video packets and 284 audio packets for the six-second case. No universal site, size, codec or speed claim is made.
