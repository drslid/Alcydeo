# Instagram post downloads — 0.1.50

Alcydeo reads the exact public post selected by an Instagram `/reel/`, `/reels/` or `/p/` URL. It reads already-loaded `application/json` data blocks, including the observed Relay `xig_logged_out_reels_feed` envelope. The post's exact shortcode and native media ID bind its catalog to the current page and frame. A different post cannot inherit it. No provider API is called, bootstrap JavaScript evaluated, account imported or signature generated.

The earlier 0.1.49 test offered **34 generic Instagram cards**, including separate playback fragments and preloaded recommendations. The supplied public Reel's native `video_versions` contained three entries with the same complete MP4 URL. The new reader folds those exact duplicates into one card, uses the post caption for its title and keeps distinct complete-file qualities on that card when the native catalog supplies them. Playback requests and recommendations do not become fallback proposals on supported post pages without an exact native catalog.

Native private/unavailable records are respected. An exact catalog with no accepted complete file is retained as an empty result, so an older accessible card cannot reappear after a native refusal. Only original HTTPS media/poster URLs on the accepted Instagram/Facebook CDN hosts are read; credentials, unusual ports, fragments and explicit byte-slice media URLs are rejected. Query parameters remain unchanged. The reader does not substitute a separate video-only playback resource for a complete file. For the tested Reel, the native VP9/video and HE-AAC/audio DASH playback manifest is not offered alongside its available complete MP4.

## Transfer and metadata

Complete MP4s use the existing Chrome download path, destination and Save As preference. Compatible multipart transfers remain an optional managed path with the existing limits. The popup can close during an ordinary native download. Managed processing still requires its manager to remain open. No additional permission, remote executable, relay or companion is added.

A bounded sample checks the real response and excludes HTML, explicit refusals and known undersized files. A `206` response's complete size comes from its validated `Content-Range` total, rather than the sample's `Content-Length`. A sample is not a full-file integrity check. Native Chrome completion and file existence acknowledge ordinary direct results; independent decoding is separate evidence.

Per-version dimensions are used only when supplied or obtained from the media itself. In this test, native `original_width`/`original_height` described **1080 × 1920**, whereas the complete downloadable MP4 actually contains **720 × 1280** video. Those original-upload dimensions are not assigned to an unspecified downloadable variant. The successful intermediate build therefore displayed **Original source** until dimensions were available. Same-URL refreshes preserve previously checked dimensions, size and codec labels without renewing their source-check timestamp.

The metadata helper can inspect the existing 4 KiB prefix and, for suitable direct ISO-BMFF files, presentation headers beyond it. Extra reads are limited to **four GET requests and 64 KiB under the shared eight-second check deadline**. They preserve the original URL and normal request context, require exact unencoded range responses and unchanged total size, and validate a strong ETag when one exists. The parser skips sample-table and media payloads; a bounded range can include adjacent bytes. It does not fetch a complete media file to discover dimensions. Missing, ambiguous or unsupported metadata stays unknown. This is advisory metadata, not strong whole-file version verification.

It retains only the minimized media fields used by existing detection/tasks, rather than raw post JSON or native account/API context.
